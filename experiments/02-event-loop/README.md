# Эксперимент 02: блокировка event loop — один процесс, `cluster`, `worker_threads`

NestJS-приложение намеренно выполняет CPU-задачу в главном потоке или в пуле потоков. Сравниваем задержки лёгких запросов, пропускную способность тяжёлых и память. У эксперимента свой `package.json`; его сборка и проверки запускаются отдельно от корневого CI. Markdown/JSON проверяет корневой Prettier.

## Запуск

Нужны Node 24 (закреплена версия 24.15.0, как в Dockerfile), Linux и локальный Docker Engine. Память измеряется через `/proc` хоста, поэтому удалённый daemon и Docker Desktop с отдельной VM не поддерживаются.

```bash
cd experiments/02-event-loop
npm ci
npm run bench                           # все 12 вариантов, примерно 13 минут
RUNS=1 DURATION=5 npm run bench          # быстрая проверка всех вариантов
npm run bench -- docker cpus=1          # фильтры по имени варианта (пересечение)
POOL_SIZE=3 npm run bench -- docker cpus=4 worker_threads
npm run check:cluster
npm run results:table                   # таблица из results.json
npm run results:table -- results.local.json
```

Полный запуск с параметрами по умолчанию сохраняет `results.json`. Быстрые и отфильтрованные запуски пишут `results.local.json` (исключён из Git); путь можно задать через `RESULTS_FILE`. Неизвестный фильтр завершает запуск с ошибкой, не меняя результатов. Отчёт записывается только после успешного завершения всех выбранных вариантов.

Параметры (положительные целые): `RUNS` (3), `DURATION` в секундах (15), `HEAVY_CONN` (4), `LIGHT_CONN` (20), `POOL_SIZE` (по умолчанию `os.availableParallelism()`). `PORT` по умолчанию 3100 и должен быть свободен.

Docker-варианты собирают образ из [Dockerfile](Dockerfile) и запускают приложение с `--network host --cpus=N`. RSS измеряется по дереву процессов контейнера. Нагрузчик работает на хосте вне квоты приложения, но конкурирует с ним за физические ресурсы. `SIGINT`/`SIGTERM` останавливают контейнер или процессы.

Ручной запуск:

```bash
npm run build
npm start                               # один процесс на :3000
WEB_CONCURRENCY=4 npm run start:cluster
```

## Устройство и методика

| Эндпоинт          | Назначение                                                                       |
| ----------------- | -------------------------------------------------------------------------------- |
| `GET /light`      | Минимальный ответ; задержка включает ожидание event loop, HTTP и планирование ОС |
| `GET /heavy`      | `pbkdf2Sync`, 20 000 итераций SHA-512 в главном потоке                           |
| `GET /heavy-pool` | То же вычисление в Piscina (`worker_threads`)                                    |
| `GET /pid`        | PID ответившего процесса                                                         |
| `GET /runtime`    | Node, доступный параллелизм, число логических CPU и параметры созданного пула    |
| `GET /crash`      | Исключение в `setTimeout`: `uncaughtException` завершает процесс                 |

- [PoolService](src/pool.service.ts) создаёт пул лениво и уничтожает при shutdown.
- [bench.mjs](scripts/bench.mjs) прогревает приложение (20 тяжёлых запросов, для baseline — лёгких), затем одновременно запускает два autocannon-нагрузчика. RSS снимается каждые 250 мс, поэтому короткие пики возможны. Каждый вариант на каждый повтор запускается заново.
- В таблице — медиана каждого показателя отдельно; диапазон p99 — минимум и максимум среди прогонов. `errors` включает `timeouts` (складывать нельзя), `non2xx` — отдельный счётчик. Таймаут autocannon — 10 секунд.
- Отчёт сохраняет commit и признак `dirty`, команду запуска, параметры нагрузки, версии runtime, настройки пула, квоту и ID образа. `dirty: true` означает, что для воспроизведения нужны и незакоммиченные изменения.

## Проверка `cluster`

[cluster.ts](src/cluster.ts) запускает `WEB_CONCURRENCY` воркеров (по умолчанию 1) и заменяет упавшие. По `SIGTERM`/`SIGINT` прекращает перезапуски, отправляет `SIGTERM` воркерам и ждёт их выхода:

- При штатном завершении всех воркеров primary выходит с кодом 0.
- По `SHUTDOWN_TIMEOUT_MS` (по умолчанию 10 000 мс) оставшиеся воркеры получают `SIGKILL`, primary выходит с кодом 1.
- После пяти последовательных падений воркеров, каждый из которых прожил меньше пяти секунд, primary прекращает crash loop, останавливает оставшихся и выходит с кодом 1.

`npm run check:cluster` собирает приложение и на реальных процессах проверяет: замену после `/crash` и `SIGKILL`; остановку зависшего воркера (`SIGSTOP`, затем deadline и `SIGKILL`, код 1); прекращение перезапусков при занятом порте; остановку по `SIGINT` и отклонение некорректных параметров.

## Что показывают замеры

| Вариант                | Наблюдение                                                              | Ограничение                                                                     |
| ---------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Один процесс           | p99 `/light` вырос с 21 до 236 мс; RPS упал с 3597 до 207               | Синхронный хэш блокирует event loop                                             |
| `cluster`, 4 воркера   | Тяжёлый RPS вырос с 30.2 до 54.5, RSS — с 126 до 559 МБ                 | Внутри каждого воркера блокировка остаётся; p99 лёгкого запроса достигал 244 мс |
| `cluster`, квота 1 CPU | Хуже одного процесса по лёгкому RPS, p50/p99, тяжёлому RPS/p99 и памяти | Результат данной нагрузки, не универсальный закон                               |
| `worker_threads`       | На хосте p99 `/light` 35 мс при 180 МБ RSS                              | Освобождает event loop, но не устраняет конкуренцию за CPU и очередь пула       |

Квота CPU (`--cpus`) и закрепление за ядрами (`taskset`/cpuset) задают разные условия планирования, их результаты нельзя смешивать. Фактический параллелизм и размер пула записываются через `/runtime`.

**Открытый вопрос:** контейнерный пул при квоте 4 CPU показал 17.1 heavy RPS против 52.7 на хосте, а при квоте 1 CPU появились таймауты. Причина (троттлинг или связка Piscina + Nest) не установлена: нужны одинаковые runtime и размеры пула, измерение CPU throttling и более длинные прогоны. Размер пула подбирайте по измерениям. CRUD поверх Postgres в первую очередь требует анализа I/O; долгие фоновые вычисления лучше выносить в очередь и отдельные worker-процессы.
