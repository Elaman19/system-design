# Эксперимент 02: блокировка event loop — один процесс, `cluster`, `worker_threads`

NestJS-приложение намеренно выполняет CPU-задачу в главном потоке или в пуле потоков. Сравниваем задержки лёгких запросов, пропускную способность тяжёлых и память. У эксперимента свой `package.json`; его сборка и проверки процессов запускаются отдельно от корневого CI. Markdown/JSON проверяет корневой Prettier.

## Запуск

Нужны Node 24, Linux и локальный Docker Engine или Podman. Скрипт измеряет память через `/proc` хоста: удалённый daemon и Docker Desktop с отдельной VM не поддерживаются. Для сопоставления с историческими числами использован Node 24.15.0; эта версия закреплена и в Dockerfile.

```bash
cd experiments/02-event-loop
npm ci
npm run bench                           # все 12 вариантов, примерно 13 минут
RUNS=1 DURATION=5 npm run bench          # быстрая проверка всех вариантов
npm run bench -- docker cpus=1          # пересечение фильтров по имени варианта
CONTAINER_ENGINE=podman npm run bench -- docker
POOL_SIZE=3 npm run bench -- docker cpus=4 worker_threads
npm run check:cluster
npm run results:table                   # таблица из сохранённого results.json
npm run results:table -- results.local.json
```

Полный запуск с параметрами по умолчанию сохраняет `results.json`. Быстрые и отфильтрованные запуски пишут `results.local.json` (исключён из Git). Можно явно задать `RESULTS_FILE=/tmp/bench.json`. Неизвестный фильтр завершает запуск с ошибкой, не меняя результаты. Отчёт записывается только после успешного завершения всех выбранных вариантов.

`RUNS`, `DURATION` (секунды), `HEAVY_CONN`, `LIGHT_CONN` и `POOL_SIZE` должны быть положительными целыми числами. По умолчанию: 3 прогона, 15 секунд, 4 тяжёлых и 20 лёгких соединений; пул использует `os.availableParallelism()`. `PORT` по умолчанию 3100 и должен быть свободен. `POOL_SIZE` передаётся и хостовым, и контейнерным вариантам.

Перед Docker-вариантами скрипт собирает образ из [Dockerfile](Dockerfile), запускает приложение с `--network host --cpus=N` и измеряет RSS дерева процессов контейнера по его host PID. Нагрузчик работает на хосте, вне квоты приложения, но конкурирует с ним за физические ресурсы. После прогона контейнер или дерево хостовых процессов останавливается; `SIGINT`/`SIGTERM` запускают ту же очистку.

Для ручного запуска:

```bash
npm run build
npm start                               # один процесс на :3000
WEB_CONCURRENCY=4 npm run start:cluster
```

## Устройство и методика

| Эндпоинт          | Назначение                                                                       |
| ----------------- | -------------------------------------------------------------------------------- |
| `GET /light`      | Минимальный ответ; задержка включает ожидание event loop, HTTP и планирование ОС |
| `GET /heavy`      | `pbkdf2Sync`, 20 000 итераций SHA-512 в главном потоке                           |
| `GET /heavy-pool` | То же вычисление в Piscina (`worker_threads`)                                    |
| `GET /pid`        | PID ответившего процесса                                                         |
| `GET /runtime`    | Node, доступный параллелизм, число логических CPU и параметры созданного пула    |
| `GET /crash`      | Исключение в `setTimeout`: `uncaughtException` завершает процесс                 |

- [PoolService](src/pool.service.ts) создаёт пул лениво и уничтожает при shutdown. `/runtime` показывает `minThreads`, `maxThreads` и текущее число потоков после прогрева; последнее не является максимумом за весь прогон.
- [bench.mjs](scripts/bench.mjs) сначала прогревает приложение 20 тяжёлыми запросами (для baseline — лёгкими), затем одновременно запускает два autocannon-нагрузчика. RSS снимается каждые 250 мс, поэтому короткие пики можно пропустить. Каждый вариант запускается заново на каждый повтор.
- В таблице медиана каждого показателя отдельно, а не один «медианный прогон». Диапазон p99 — минимум и максимум среди прогонов. `errors`, `timeouts` и `non2xx` суммируются по всем повторам и обоим нагрузчикам.
- В новых отчётах `errors` уже включает `timeouts`; складывать их нельзя. `non2xx` — отдельный счётчик HTTP-ответов с неуспешным статусом. Таймаут autocannon — 10 секунд. p99 успешных измеренных ответов не заменяет счётчики ошибок.
- Отчёт сохраняет commit и признак изменённого рабочего дерева, команду запуска, параметры нагрузки, версию runtime каждого варианта, настройки пула, квоту и ID образа. `dirty: true` означает, что одного commit недостаточно для воспроизведения: нужны также незакоммиченные изменения.

## Проверка `cluster`

[cluster.ts](src/cluster.ts) запускает `WEB_CONCURRENCY` воркеров (по умолчанию 1) и заменяет упавшие. По `SIGTERM`/`SIGINT` прекращает перезапуски, отправляет `SIGTERM` воркерам и ждёт их выхода:

- При штатном завершении всех воркеров primary выходит с кодом 0.
- По `SHUTDOWN_TIMEOUT_MS` (по умолчанию 10 000 мс) оставшиеся воркеры получают `SIGKILL`; после их выхода primary завершается с кодом 1.
- После пяти последовательных падений воркеров, каждый из которых прожил меньше пяти секунд, primary прекращает crash loop, останавливает оставшихся и выходит с кодом 1. Это число падений, а не число полных перезапусков группы.

`npm run check:cluster` собирает приложение и проверяет реальные процессы:

1. Замену после `/crash` и после `SIGKILL`, доступность HTTP, остановку по `SIGTERM` без новых fork.
2. Остановку зависшего воркера: `SIGSTOP` блокирует реакцию на `SIGTERM`, затем deadline приводит к `SIGKILL` и коду 1.
3. Прекращение перезапусков при занятом порте.
4. Штатную остановку по `SIGINT` и отклонение некорректных параметров.

Проверка также ждёт исчезновения наблюдавшихся воркеров. Конкретные PID и длительности в документацию не копируются.

## Что показывают замеры

| Вариант                | Наблюдение в историческом запуске                                       | Ограничение                                                                                |
| ---------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Один процесс           | p99 `/light` вырос с 21 до 236 мс; RPS упал с 3597 до 207               | Синхронный хэш блокирует event loop                                                        |
| `cluster`, 4 воркера   | Тяжёлый RPS вырос с 30.2 до 54.5, RSS — с 126 до 559 МБ                 | Внутри каждого воркера блокировка остаётся; p99 лёгкого запроса достигал 244 мс            |
| `cluster`, квота 1 CPU | Хуже одного процесса по лёгкому RPS, p50/p99, тяжёлому RPS/p99 и памяти | Счётчик ошибок у обоих нулевой; это результат данной нагрузки, не универсальный закон      |
| `worker_threads`       | На хосте p99 `/light` 35 мс при 180 МБ RSS                              | Вынос вычислений освобождает event loop, но не устраняет конкуренцию за CPU и очередь пула |

С keep-alive `cluster` распределяет соединения между воркерами. От того, куда попали тяжёлые соединения, зависит задержка лёгких; три повтора не дают надёжной оценки устойчивости распределения. Четыре тяжёлых соединения также ограничивают число одновременно выполняемых тяжёлых запросов.

Квота CPU (`--cpus`) и закрепление за ядрами (`taskset`/cpuset) задают разные условия планирования. Их результаты нельзя напрямую смешивать. Фактически доступный параллелизм и размер пула теперь записываются через `/runtime`, а не выводятся из числа CPU хоста.

**Открытый вопрос:** в старом запуске контейнерный пул при квоте 4 CPU показал 17.1 heavy RPS против 52.7 на хосте. В исходных заметках также упоминались отдельные пробы `POOL_SIZE=3`, отсутствие лёгкой нагрузки и голые `Worker`, но их команды и сырые результаты не сохранены. Этого недостаточно, чтобы исключить троттлинг или приписать проблему связке Piscina + Nest. Причина снижения throughput и таймаутов при квоте 1 CPU остаётся неустановленной.

Для дальнейшего исследования нужны одинаковые runtime и размеры пула, сохранённые результаты каждого варианта, измерение CPU throttling и более длинные повторные прогоны. Подбирать размер пула следует по измерениям. CRUD поверх Postgres прежде всего требует анализа I/O; длительные фоновые вычисления можно вынести в очередь и отдельные worker-процессы.
