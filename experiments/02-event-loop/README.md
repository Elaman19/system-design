# Эксперимент 02: блокировка event loop — один процесс, `cluster`, `worker_threads`

Одна проблема — три способа с ней жить. Маленькое NestJS-приложение намеренно блокирует event loop. Оно живёт отдельно от основного проекта: свой `package.json`, исключено из корневого `tsc`, в корневой `npm run ci` не входит.

## Запуск

```bash
cd experiments/02-event-loop
npm ci
npm run bench                       # сборка + все варианты, ~7 минут, печатает таблицу и пишет results.json
RUNS=1 DURATION=5 npm run bench     # быстрый прогон

npm run build
npm start                                   # вариант 1 и 3: один процесс на :3000
WEB_CONCURRENCY=4 npm run start:cluster     # вариант 2
```

Нужны Node 24 и Linux: память меряется через `/proc`, а один CPU эмулируется через `taskset`.

## Что внутри

| Эндпоинт          | Что делает                                                                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------------------- |
| `GET /light`      | ничего: его латентность = сколько запрос ждёт свободный event loop                                              |
| `GET /heavy`      | `pbkdf2Sync`, 20 000 итераций SHA-512, ~45 мс чистого CPU **в главном потоке**                                  |
| `GET /heavy-pool` | то же вычисление в пуле `worker_threads` ([piscina](https://github.com/piscinajs/piscina)), размер = числу ядер |
| `GET /crash`      | бросает исключение в `setTimeout`, то есть `uncaughtException`, и процесс падает (для проверки `cluster`)       |
| `GET /pid`        | pid процесса, который ответил                                                                                   |

- [`src/cluster.ts`](src/cluster.ts) — число воркеров из `WEB_CONCURRENCY` (по умолчанию 1). Упавший воркер форкается заново. По `SIGTERM`/`SIGINT` primary ставит флаг `shuttingDown`, шлёт `SIGTERM` всем воркерам, **не** перезапускает их и выходит, когда последний завершился.
- [`src/pool.service.ts`](src/pool.service.ts) — пул создаётся лениво, чтобы не раздувать память вариантов 1 и 2, и закрывается на shutdown.
- [`scripts/bench.mjs`](scripts/bench.mjs) — поднимает вариант, прогревает, затем **одновременно** даёт нагрузку [autocannon](https://github.com/mcollina/autocannon): 4 соединения на тяжёлый эндпоинт и 20 на `/light`, по 15 с. Каждые 250 мс снимает RSS всего дерева процессов. Каждый вариант повторяется 3 раза, в таблице медиана.

## Проверка `cluster`: перезапуск и остановка

```text
$ WEB_CONCURRENCY=2 PORT=3111 node dist/cluster.js
primary 6214 started 2 workers
$ curl localhost:3111/crash        → {"crashing":6230}
Error: boom
worker 6230 died (1), forking a replacement     # воркеры были 6230 6231 → стали 6231 6264
$ kill -TERM 6214
SIGTERM: stopping 2 workers, no restarts
all workers stopped, primary exiting           # код выхода 0, ни одного node-процесса не осталось
```

## Вывод

| Вариант               | Что чинит                                                                                                                                          | Чего не чинит                                                                                                                                                             |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Один процесс       | —                                                                                                                                                  | Каждый хэш на ~45 мс останавливает **все** запросы: p99 `/light` вырос с 10 до 163 мс, RPS упал в 19 раз (5243 → 274)                                                     |
| 2. `cluster`          | Пропускная способность тяжёлого эндпоинта: 40 → 62–64 RPS. Падение одного воркера не роняет сервис                                                 | Блокировку. Лёгкий запрос попадает на воркер, занятый хэшем: p99 на 4 воркерах — 156 мс, почти как без кластера. Память растёт линейно: 565 МБ на 4 воркера против 109 МБ |
| 2. `cluster` на 1 CPU | Ничего по скорости: тяжёлый RPS 28 против 40 у одного процесса, лишние процессы только делят ядро                                                  | —                                                                                                                                                                         |
| 3. `worker_threads`   | Event loop свободен: p99 `/light` 17 мс, почти как baseline (10 мс), RPS 3577. Тяжёлый эндпоинт не медленнее кластера (64.5 RPS) при памяти 180 МБ | Сами вычисления не ускоряются, просто идут в другом потоке. Пул ограничен ядрами. Упавший процесс теряет задачи в пуле                                                    |

Что видно в цифрах:

- **`cluster` балансирует соединения, а не запросы.** autocannon держит keep-alive, поэтому каждое соединение навсегда привязано к своему воркеру. Отсюда разброс: в одном прогоне 4 воркеров лёгкий RPS был 2591, а в двух других — около 350. Всё зависит от того, легли ли 4 тяжёлых соединения на все 4 воркера или два из них оказались на одном.
- **Тяжёлый RPS упирается в нагрузку, а не в ядра.** На тяжёлом эндпоинте 4 соединения, значит, одновременно считается не больше 4 хэшей. Поэтому 2 воркера, 4 воркера и пул из 8 потоков дают одинаковые ~64 RPS. Чтобы увидеть потолок по ядрам, нужно поднять `HEAVY_CONN`.
- **На одном CPU у кластера p50 `/light` = 2 мс** — лучше, чем на 8 ядрах. ОС вытесняет процессы по таймеру, и воркер без хэша получает квант времени, не дожидаясь конца чужого хэша. Внутри одного event loop такого вытеснения нет: колбэк работает, пока не вернёт управление. Платой стал тяжёлый RPS (28). Вывод: `cluster` в контейнере с `--cpus=1` не даёт ничего, кроме лишней памяти.

**Для моего проекта:** `worker_threads` нужны только для редких коротких CPU-задач в ответе на запрос — хэш пароля (точнее, async `crypto`, который и так уходит в пул libuv), разбор большого файла при импорте. CRUD поверх Postgres упирается в I/O, и там потоки ничего не дадут. Долгие задачи (отчёты, медиа) — в очередь и отдельный воркер. Масштабирование по ядрам — репликами контейнеров, а не `cluster`.
