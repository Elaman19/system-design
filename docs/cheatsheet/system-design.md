## Статика и SPA

Где раздавать HTML, JavaScript, CSS и изображения?

| Вариант                    | Когда удобен                                                | Компромисс                                                                                        |
| -------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Node.js (`express.static`) | Небольшое приложение, внутренняя панель, простой deployment | Статика использует ресурсы приложения и масштабируется вместе с API                               |
| Nginx                      | VM/VPS, on-premise, frontend рядом с backend                | Нужно обслуживать конфигурацию и сервер; доступны reverse proxy, TLS, compression и cache headers |
| Object storage + CDN       | Независимый deployment SPA, пользователи в разных регионах  | Нужно настроить origin, доступ, кеширование и маршрутизацию SPA                                   |

```text
Browser ──► CDN ──► Object storage (HTML, JS, CSS)
   │
   └──────► Load balancer ──► Node.js API
```

Для файлов с хешем в имени (`app.a81f7c.js`) подходит длительный кеш:

```http
Cache-Control: public, max-age=31536000, immutable
```

Для `index.html` нужна проверка актуальности, например:

```http
Cache-Control: no-cache
```

`no-cache` допускает хранение ответа, но требует проверки перед повторным использованием. Старые assets стоит сохранять на время перехода между релизами, чтобы открытые вкладки могли загрузить свои chunks.

## Layer и tier

**Layer** — логический слой кода. **Tier** — отдельная часть развертывания с процессной или сетевой границей.

```text
Browser                         Presentation tier
   │ HTTPS
   ▼
Node.js                         Application tier
   ├── Controller layer
   ├── Business/service layer
   └── Repository layer
   │ SQL/TCP
   ▼
PostgreSQL                      Data tier
```

Перенос `Repository` в другую папку меняет организацию кода. Перенос в отдельный сервис добавляет сетевые вызовы, задержки и независимые отказы. Разрезать сервисы по слоям обычно невыгодно: логическая связность остаётся, а стоимость взаимодействия растёт.

## Компоненты веб-приложения

| Компонент           | Ответственность                                                                     |
| ------------------- | ----------------------------------------------------------------------------------- |
| DNS                 | Разрешить имя в адрес входной точки; это отдельный шаг до HTTP-запроса              |
| CDN / WAF           | Кешировать ответы у пользователя / фильтровать трафик                               |
| Load balancer       | Направлять трафик на здоровые инстансы приложения                                   |
| Application servers | HTTP/API, проверка входных данных, бизнес-логика                                    |
| Database            | Постоянные данные, транзакции и ограничения целостности                             |
| Cache               | Ускорять повторные чтения; требует стратегии TTL/инвалидации                        |
| Queue               | Отделять приём работы от выполнения, сглаживать пики                                |
| Workers             | Выполнять фоновые задачи с retry и защитой от повторной обработки                   |
| Поиск               | Полнотекстовый поиск с релевантностью (Elasticsearch, Solr), когда поиска в БД мало |
| Мониторинг и алерты | Метрики, логи, traces; алерты сообщают команде о проблеме                           |
| CI/CD               | Автоматическая сборка, проверка и выкладка на инстансы                              |

```text
Client ──► CDN/WAF ──► Load balancer ──► App instances
                                           ├──► Database
                                           ├──► Cache
                                           └──► Queue ──► Workers ──► Database / Object storage
```

Не каждому приложению нужны все компоненты (список близок к карте ByteByteGo «10 Essential Components»). Добавляй их под измеренную нагрузку, требования к надёжности и характер задач. Долговечность очереди зависит от выбранной системы и настроек подтверждения/хранения сообщений.

## Балансировщик

Помимо распределения трафика, балансировщик может выполнять health checks, исключать нездоровые инстансы, завершать TLS и маршрутизировать запросы по host/path. Конкретные возможности зависят от уровня и реализации балансировщика.

Балансировщик помогает использовать несколько инстансов, но сам не создаёт вычислительные ресурсы. Autoscaler отдельно решает, сколько инстансов нужно. Readiness определяет готовность принимать трафик; liveness — необходимость перезапуска.

| Проверка  | Вопрос                       | Кто реагирует и как                      |
| --------- | ---------------------------- | ---------------------------------------- |
| Startup   | Приложение закончило запуск? | Платформа откладывает остальные проверки |
| Liveness  | Процесс завис безвозвратно?  | Платформа перезапускает контейнер        |
| Readiness | Можно слать трафик?          | Инстанс исключается из маршрутизации     |

Зависимости (БД) проверяй в readiness, не в liveness: иначе при отказе БД все реплики перезапустятся разом и усугубят сбой. Liveness — только про сам процесс. `healthcheck` в Docker Compose лишь выставляет статус `healthy`/`unhealthy` (его использует `depends_on: service_healthy`); сам по себе он не перезапускает контейнер и не выводит его из балансировки.

## Границы сервисов

Разделение на отдельные сервисы «API», «бизнес-логика» и «данные» часто создаёт распределённый монолит: один сценарий проходит через все сервисы, а менять и выкатывать их приходится совместно.

Более полезные границы — бизнес-возможности или bounded contexts: Orders, Payments, Catalog. У сервиса есть свой контракт, логика и ответственность за данные. Владение данными не обязательно означает отдельный физический сервер БД, но другие сервисы не должны обходить контракт прямой записью в его таблицы.

Проверочные вопросы:

- Можно ли изменить и развернуть эту часть независимо?
- Где проходит транзакционная граница?
- Что произойдёт при задержке, отказе или повторе сетевого вызова?
- Оправдывает ли независимое масштабирование дополнительную сложность?

Модульный монолит часто достаточен. Микросервисы требуют работы с таймаутами, retry, идемпотентностью, согласованностью данных и наблюдаемостью.

## Cloud-native и cloud-enabled

**Cloud-enabled** — существующее приложение перенесено в облачную инфраструктуру с небольшими изменениями, например с локальной VM на EC2.

**Cloud-native** (AWS описывает его через immutable infrastructure, контейнеры, API, CI/CD; CNCF добавляет микросервисы и service mesh как примеры) — архитектура учитывает заменяемые инстансы, автоматизацию deployment, внешнее состояние, масштабирование и отказы инфраструктуры. Managed services могут сократить эксплуатационную работу. Микросервисы и Kubernetes не обязательны.

## 12-Factor App

| Фактор              | Суть                                                                             |
| ------------------- | -------------------------------------------------------------------------------- |
| Codebase            | Одна кодовая база приложения, много deployments                                  |
| Dependencies        | Явно объявлять и изолировать зависимости                                         |
| Config              | Всё, что меняется между deployments (адреса БД, ключи), хранить в env, не в коде |
| Backing services    | Рассматривать БД, кеш и очереди как подключаемые ресурсы                         |
| Build, release, run | Разделять сборку, релиз и запуск                                                 |
| Processes           | Хранить долговечное состояние вне процессов приложения                           |
| Port binding        | Приложение экспортирует сервис через порт                                        |
| Concurrency         | Масштабировать приложение процессами                                             |
| Disposability       | Быстрый startup и корректный shutdown                                            |
| Dev/prod parity     | Сокращать различия окружений                                                     |
| Logs                | Отдавать логи как поток событий                                                  |
| Admin processes     | Запускать миграции и служебные задачи отдельными процессами в окружении релиза   |

Для Node.js особенно полезны внешняя конфигурация, stateless-процессы, масштабирование процессами, graceful shutdown и логи в stdout/stderr. Секреты не должны попадать в репозиторий или логи.

## Одноразовые контейнеры

Инстанс можно остановить и заменить. Новый контейнер не обязан иметь память или writable filesystem предыдущего.

| Состояние / работа                          | Где хранить или выполнять                       |
| ------------------------------------------- | ----------------------------------------------- |
| Сессии, которым нужен общий серверный state | Redis / DB                                      |
| Пользовательские файлы                      | Object storage или другое долговечное хранилище |
| Постоянные данные                           | DB / persistent storage                         |
| Временные файлы                             | Локально, если их потеря допустима              |
| Важные фоновые задачи                       | Долговечная очередь + workers                   |
| Логи                                        | stdout/stderr + внешний сборщик                 |

`setTimeout(() => sendEmail(), 60_000)` потеряет работу при завершении процесса. Для важных задач нужны сохранение задания, подтверждения, retry и идемпотентность. Cron внутри каждой web-реплики может запустить одну задачу несколько раз.

## Graceful shutdown

По `SIGTERM` приложение должно:

1. Пометить себя как shutting down / not ready.
2. Перестать принимать новую работу: HTTP-запросы и сообщения очереди.
3. Дождаться уже начатых запросов и задач в пределах установленного срока.
4. Закрыть DB/Redis/queue connections и другие ресурсы.
5. Завершить отправку логов/телеметрии и выйти.

В NestJS: `app.enableShutdownHooks()` (по умолчанию выключено), затем хуки `onModuleDestroy` → `beforeApplicationShutdown` → закрытие соединений → `onApplicationShutdown`. Пауза `gracefulShutdownTimeoutMs` в Terminus (по умолчанию 0, только для `SIGTERM`) отдаёт 503 в health-check, чтобы балансировщик успел убрать инстанс; ожидание активных запросов — отдельная задача. С Node.js 19 `server.close()` сам закрывает idle keep-alive соединения, но активным запросам всё равно нужен deadline. В контейнере Node как PID 1 может не получать сигналы — используй `init: true` / `--init`. По умолчанию `docker compose stop` ждёт 10 секунд до `SIGKILL` (`stop_grace_period`), Heroku и Kubernetes — 30.

Нужны общий deadline и защита от повторного запуска shutdown. Ресурсы закрываются после работы, которая ими пользуется. Readiness и исключение из балансировки могут распространяться с задержкой — порядок drain должен учитывать платформу.

```text
SIGTERM ──► stop new work ──► drain ──► close resources ──► exit
                              │
                              └── deadline exceeded ──► forced termination
```

Почему трафик приходит и после `SIGTERM` (Kubernetes): удаление из endpoints идёт параллельно с остановкой, а kube-proxy и ingress узнают об этом с разной задержкой. Поэтому перед закрытием сервера делают паузу (`preStop: sleep` или ожидание в приложении, порядка 15 с), и она входит в `terminationGracePeriodSeconds`.

```text
время ─────────────────────────────────────────────────────────────►
Платформа:   пометка Terminating ─► обновление endpoints/LB (с задержкой)
Приложение:  preStop / пауза ─► SIGTERM ─► drain ─► close ─► exit
                            └──── общий deadline (30 с) ────► SIGKILL
```

Graceful shutdown не защищает от `SIGKILL` и аварии машины. Для критичной работы всё равно нужны транзакции, долговечное состояние, retry и идемпотентность.

## Масштабирование

|              | Вертикальное (scale up)                                | Горизонтальное (scale out)                               |
| ------------ | ------------------------------------------------------ | -------------------------------------------------------- |
| Что меняем   | CPU/RAM одного инстанса                                | Количество инстансов                                     |
| Преимущество | Меньше изменений архитектуры                           | Независимая ёмкость и возможность пережить отказ реплики |
| Ограничение  | Предел машины; возможен downtime при изменении размера | Координация, распределённое состояние, сетевые отказы    |
| Надёжность   | Один инстанс может остаться SPOF                       | Нужны балансировка и размещение в разных доменах отказа  |

Дополнительные ядра не заставляют один JS event loop исполнять JavaScript параллельно. Для CPU-задач используются процессы или `worker_threads`; асинхронное I/O решает другую задачу. См. [эксперимент с event loop](../../experiments/02-event-loop/README.md).

Приложение и БД масштабируются по-разному. Для БД сначала стоит исследовать запросы, индексы, блокировки и лимиты ресурсов. Реплики чтения не распределяют запись между узлами и могут отставать; вынос чтений на реплики лишь косвенно разгружает primary. Шардинг добавляет сложность маршрутизации и транзакций. На практике scale up и scale out часто сочетаются.

### Карта роста по сигналам

Каждый компонент добавляется в ответ на измеренную проблему (идея — глава ByteByteGo «Scale From Zero To Millions»: один сервер → отдельная БД → балансировщик → реплики → кеш → CDN → stateless-веб-слой → очередь → мониторинг → шардинг). Ветки независимы:

```text
Какое ограничение подтверждено?
 ├─ CPU приложения / event-loop lag  ─► оптимизация, больше реплик API
 ├─ Долгие повторяющиеся чтения      ─► запросы и индексы ─► кеш / реплики чтения
 ├─ Долгая фоновая работа            ─► долговечная очередь + workers
 ├─ Медленная статика                ─► object storage + CDN
 └─ Поиск с релевантностью           ─► отдельный поисковый индекс
```

## Cluster или несколько контейнеров

`cluster` запускает несколько процессов Node.js внутри одного контейнера. Альтернатива — один процесс на контейнер и несколько контейнеров.

| Критерий        | `cluster` в контейнере                                       | Несколько инстансов контейнера                   |
| --------------- | ------------------------------------------------------------ | ------------------------------------------------ |
| Использует ядра | Да, в пределах одного контейнера                             | Да, каждый контейнер — отдельный процесс         |
| Перезапуск      | Master перезапускает воркеры; платформа видит один контейнер | Платформа перезапускает упавший контейнер        |
| Health checks   | Проверка видит master/один порт, а не каждый воркер          | Readiness/liveness работают для каждого инстанса |
| Масштабирование | Ограничено размером контейнера                               | Autoscaler добавляет и убирает инстансы          |
| Лимиты ресурсов | CPU/RAM делят все воркеры                                    | Лимиты и метрики на каждый процесс               |
| Shutdown        | Master должен пробросить `SIGTERM` и дождаться воркеров      | Платформа шлёт `SIGTERM` процессу напрямую       |

В облаке по умолчанию выбирай несколько инстансов с одним процессом: оркестратор уже умеет перезапуск, балансировку, health checks и autoscaling, а `cluster` дублирует эти функции. Если у контейнера лимит в 1 vCPU, `cluster` ничего не даёт.

`cluster` оправдан на VM/VPS без оркестратора, где нужно занять все ядра одним сервисом, либо когда накладные расходы на инстанс (память, соединения с БД) слишком высоки. Это не отменяет требований к stateless и graceful shutdown: воркеры не делят память друг с другом.

## Облако или свои серверы

Стабильные 2000 RPS без всплесков и команда, умеющая эксплуатацию, — это случай, где главное преимущество облака (эластичность) почти не используется. Нагрузка умеренная: обычно хватает нескольких инстансов приложения, итог зависит от стоимости запроса.

| Фактор             | Облако                                                  | Свои серверы                                          |
| ------------------ | ------------------------------------------------------- | ----------------------------------------------------- |
| Нагрузка           | Выигрывает при всплесках и неопределённом росте         | Выигрывает при стабильной и предсказуемой нагрузке    |
| Стоимость          | Оплата по использованию; reserved/savings plans дешевле | Capex на железо, плюс стойка, питание, сеть, запас    |
| Эксплуатация       | Managed-сервисы снимают часть работы                    | Нужны люди: обновления, бэкапы, мониторинг, дежурства |
| Надёжность         | Зоны доступности «из коробки»                           | Резервирование, второй сайт и DR строишь сам          |
| Скорость изменений | Ресурсы за минуты                                       | Закупка и монтаж занимают недели                      |
| Трафик             | Исходящий трафик (egress) тарифицируется                | Оплачивается канал, а не гигабайты                    |

Как обосновать решение:

1. Посчитать TCO на 3–5 лет для обоих вариантов: железо и амортизация, стойка/colo, питание и охлаждение, сеть, лицензии, запасные части, зарплаты, egress, managed-сервисы.
2. Учесть требования к доступности: два сайта, бэкапы и восстановление стоят денег и у своих серверов.
3. Измерить p95/p99 при 2000 RPS нагрузочным тестом на обоих вариантах, а не сравнивать только среднюю задержку.
4. Оценить риски: срок закупки, отказ железа, нехватка людей, привязка к вендору.

Итог зависит от цифр. При стабильной нагрузке и сильной команде свои серверы или аренда выделенных машин часто дешевле, а облако дороже за те же ресурсы. Гибридный вариант: базовую нагрузку держать на своих серверах, пики и DR — в облаке. Если команда мала или рост неясен, облако снижает операционный риск, даже при более высокой цене.

## C4: четыре уровня

C4 — модель описания архитектуры «от общего к частному». Уровни: Context, Containers, Components, Code.

| Уровень      | Что показывает                                      | Для кого                              |
| ------------ | --------------------------------------------------- | ------------------------------------- |
| 1. Context   | Система, её пользователи и внешние системы          | Бизнес, продукт, архитекторы, команда |
| 2. Container | Приложения, сервисы и хранилища, технологии и связи | Архитекторы, tech leads, DevOps       |
| 3. Component | Внутренняя структура одного контейнера              | Разработчики, tech leads              |
| 4. Code      | Классы и интерфейсы                                 | Разработчики                          |

```text
L1 Context      Клиент ──► Площадка ──► Платёжная система
L2 Container    SPA ──► Node.js API ──► PostgreSQL
L3 Component    внутри API: Invoices controller, Payments service, Repository
L4 Code         классы и интерфейсы Payments service
```

На практике чаще рисуют уровни 1 и 2; Component — для сложных контейнеров, Code обычно заменяет сам код и генерируемые схемы. На вопрос об архитектуре сначала назови уровень, на котором отвечаешь. У каждого элемента подпись с технологией, у каждой стрелки — глагол и протокол.

## Контейнер в C4 и Docker-контейнер

**Контейнер в C4** — отдельно запускаемое приложение или хранилище данных (Node.js API, SPA, PostgreSQL). Это логическая единица архитектуры. **Docker-контейнер** — единица запуска и изоляции процесса. C4 отвечает на вопрос «из чего состоит система», Docker — «как это запускается».

Они не совпадают, когда:

| Случай                                              | C4 Container        | Docker-контейнеры                   |
| --------------------------------------------------- | ------------------- | ----------------------------------- |
| Node.js API в 10 репликах за балансировщиком        | Один: `Node.js API` | Десять                              |
| SPA в object storage + CDN                          | Один: `SPA`         | Ноль — Docker не используется       |
| Managed PostgreSQL (RDS)                            | Один: `PostgreSQL`  | Ноль — запускает облачный провайдер |
| Приложение и sidecar (прокси, сборщик логов) в поде | Обычно один или два | Два, запущенных вместе              |

```text
C4 Container: Node.js API
 ├── Docker replica 1
 ├── Docker replica 2
 └── Docker replica 3
```

Сам C4 подчёркивает: контейнер — это «не Docker», а runtime-граница вокруг исполняемого кода или хранимых данных; serverless-функции, mobile-приложения и S3 тоже контейнеры C4. Реплики на диаграмме контейнеров обычно не рисуют: количество инстансов, узлы и зоны доступности показывает Deployment-диаграмма.

## Порядок ответа на system design

1. Требования (функциональные и нефункциональные) и ограничения.
2. Оценка нагрузки и объёма данных.
3. High-level схема: клиент, API, хранилища, очередь, кеш.
4. Разбор узкого места и выбранных компонентов.
5. Отказы, компромиссы и план роста.
