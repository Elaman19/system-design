# ADR 0015. Real-time: ws-gateway и Redis Streams

**Статус:** предложено (зона 6, ещё не реализовано).

## Контекст

Покупатель держит карточку лота открытой, а цену или остаток меняют (в том числе чужие покупки). Сейчас он узнаёт об этом только по перезагрузке или по ошибке покупки. Нужна рассылка событий «лот продан», «цена изменилась», «остаток изменился». Разбор общей задачи (три инстанса, 15 000 подключений) — в [docs/highload](../../../highload/README.md#213-websocket).

Предпосылка: сейчас у площадки **нет входа** (L1: «входа и интерфейса пока нет»). Подписка на события без аутентификации возможна только на публичные события о лотах; личные события (чек, баланс кошелька) требуют входа и билета для WebSocket, и это отдельное решение.

## Варианты

1. **Redis Pub/Sub.** Просто, но копия, которая в этот момент перезапускалась, событие пропускает; повтора нет.
2. **Redis Streams** (отдельный Redis): события с возрастающим id, копии читают поток, клиент при возврате шлёт `lastEventId`.
3. **Kafka** (она уже есть): топик `lot-events`, у каждой копии шлюза своя группа. Платим тем, что оффсеты и группы не годятся как «id события для клиента», на каждую копию своя группа и ребалансы; Kafka тяжелее для миллисекундной доставки.
4. **Управляемый сервис** (Ably, Pusher). Платим деньгами, привязкой и тем, что чужие сервисы получают данные площадки.

## Выбор

**Вариант 2.**

- **Источник событий — `outbox-relay`, а не `app` напрямую.** Транзакция меняет лот и пишет строку в `outbox`, релей кладёт её в поток. Прямая запись в Redis после COMMIT повторила бы двойную запись из [ADR 0006](../../marketplace-v3/adr/0006-outbox-bullmq.md): упали между COMMIT и `XADD` — событие потеряно. Нужна миграция: `outbox_kind_known` сейчас допускает только `deal.receipt`.
- Событие: `{ id, type, lotId, price, stock }`; `type` — `lot.sold`, `lot.price_changed`, `lot.stock_changed`. Клиент подписывается на свои лоты (до 50); шлюз отдаёт ему только их.
- **Отдельный Redis** для потока: кэш можно вытеснять ([ADR 0012](0012-cache-cards-and-bans.md)), очередь и поток нельзя.
- Хвост потока 5 минут (`MINID`): при 10 событиях в секунду и ~200 байтах это ~600 КБ.
- ws-gateway — **отдельный контейнер**, не часть `app`: долгие соединения и остановка при деплое не должны мешать обычному API. Копий N, по 5 000 соединений.

## Последствия

- Доставка клиенту **хотя бы раз**, с id для дедупликации; порядок внутри потока. Нет порядка между потоками разных видов.
- Redis с потоком недоступен: соединения живут, события задерживаются в `outbox` (релей повторяет), потерь нет. После возврата клиенты получают пропущенное по `lastEventId` либо `resync`, если хвоста не хватило.
- Деплой: копия снимается с балансировки по `/ready`, закрывает соединения кодом `1001`, клиенты возвращаются с экспоненциальной паузой и jitter. Запас ёмкости N+1.
- Исходящая рассылка — главный потолок: ~50 000 сообщений в секунду на копию. Лекарство при росте: подписки по лотам и объединение кадров.
- Цена по сравнению с опросом: ещё один контейнер, один Redis и долгие соединения за балансировщиком (idle-таймаут, ping/pong).
