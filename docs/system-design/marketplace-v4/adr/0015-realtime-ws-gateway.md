# ADR 0015. Real-time: ws-gateway и Redis Streams

**Статус:** предложено (зона 6, ещё не реализовано).

## Контекст

Покупатель держит карточку лота открытой, а цену или остаток меняют (в том числе чужие покупки). Сейчас он узнаёт об этом только по перезагрузке или по ошибке покупки. Нужна рассылка событий «лот продан», «цена изменилась», «остаток изменился». Разбор общей задачи (три инстанса, 15 000 подключений, событие всем) — в [docs/highload](../../../highload/README.md#213-websocket).

Предпосылка: сейчас у площадки **нет входа** (L1: «входа и интерфейса пока нет»). Подписка на события без аутентификации возможна только на публичные события о лотах; личные события (чек, баланс кошелька) требуют входа и билета для WebSocket, и это отдельное решение.

## Варианты

1. **Redis Pub/Sub.** Просто, но копия, которая в этот момент перезапускалась, событие пропускает; повтора нет.
2. **Redis Streams** (отдельный Redis): события с возрастающим id, копии читают поток, клиент при возврате шлёт `lastEventId`.
3. **Kafka** (она уже есть): топик `lot-events`. Пара (партиция, оффсет) — нормальный id события, а `assign()` без группы обходится без ребалансов, так что дело не в этом. Платим другим: задержка доставки выше (пачки, `linger`, опрос), на каждое переподключение клиента шлюз читает с произвольного оффсета, а этот режим Kafka обслуживает хуже, чем хвост потока в памяти Redis; и Kafka — ещё один кластер в эксплуатации для задачи, где хватает 600 КБ хвоста.
4. **Управляемый сервис** (Ably, Pusher). Платим деньгами, привязкой и тем, что чужие сервисы получают данные площадки.

## Выбор

**Вариант 2.**

- **Источник событий — `outbox-relay`, а не `app` напрямую.** Транзакция меняет лот и пишет строку в `outbox`, релей кладёт её в поток. Прямая запись в Redis после COMMIT повторила бы двойную запись из [ADR 0006](../../marketplace-v3/adr/0006-outbox-bullmq.md): упали между COMMIT и `XADD` — событие потеряно. Нужна миграция: `outbox_kind_known` сейчас допускает только `deal.receipt`.
- **Отдельный проход релея на каждое назначение.** Сейчас один проход — одна транзакция по всем строкам `ORDER BY id`, и любая ошибка откатывает всю пачку ([src/outbox/outbox-relay.service.ts](../../../../src/outbox/outbox-relay.service.ts)). Если на тот же проход повесить `XADD`, недоступный Redis потока остановит и чеки. Поэтому у каждого `kind` свой цикл (`WHERE kind = $1`, свой частичный индекс, своя пауза при ошибках): чеки идут в BullMQ, события лотов — в поток, и отказ одного назначения не задерживает другое.
- **Событие несёт версию лота.** Событие: `{ id, type, lotId, version, price, stock }`; `type` — `lot.sold`, `lot.price_changed`, `lot.stock_changed`. `version` — счётчик в строке `lots`, увеличивается в той же транзакции, что меняет цену или остаток (строка лота и так под `FOR UPDATE` или `UPDATE`, поэтому версии одного лота выдаются строго по порядку коммитов). Это нужно потому, что id строки `outbox` выдаётся при `INSERT`, а не при COMMIT: транзакция T1 получила id 10, T2 — id 11, T2 закоммитилась первой — релей отдаст 11, потом 10, и без версии клиент перезаписал бы новую цену старой. **Правило клиента:** событие с `version` не больше известной отбрасывается; `version` больше известной на 2 и более — пропуск, клиент делает `resync` через `GET /lots/:id`. Нужна миграция: колонка `lots.version`.
- Клиент подписывается на свои лоты (до 50); шлюз отдаёт ему только их.
- **Поток не в одном Redis с кэшем:** кэш можно вытеснять ([ADR 0012](0012-cache-cards-and-bans.md)), очередь и поток нельзя. С очередью BullMQ делить экземпляр можно (см. «Цена Redis» в [README](../README.md#цена-redis-пять-ролей)).
- Хвост потока 5 минут (`MINID`): при 10 событиях в секунду и ~200 байтах это ~600 КБ.
- ws-gateway — **отдельный контейнер**, не часть `app`: долгие соединения и остановка при деплое не должны мешать обычному API. Копий N, по 5 000 соединений; балансировщик по least-connections.

## Последствия

- Доставка клиенту **хотя бы раз**, с id для дедупликации и версией лота для порядка. Порядок в потоке — порядок `XADD`, не коммитов: на него клиент не полагается.
- Redis с потоком недоступен: соединения живут, события задерживаются в `outbox` (релей повторяет), чеки при этом уходят (свой проход). После возврата клиенты получают пропущенное по `lastEventId` либо `resync`, если хвоста не хватило.
- **Failover Redis теряет хвост:** реплика асинхронная, а строки `outbox` уже помечены отправленными. «Потерь нет» здесь неверно. Клиент обнаружит потерю по версии лота при следующем событии и сделает `resync`; если следующего события по лоту нет, устаревшая цена видна до него или до повторного открытия карточки. Деньги не страдают: покупка проверяет цену и остаток в базе.
- Деплой: копия снимается с балансировки по `/ready`, закрывает соединения кодом `1001` порциями, клиенты возвращаются с паузой и jitter. Запас ёмкости N+1.
- **Нагрузка на рассылку при подписке по лотам мала.** 10 событий в секунду по всем лотам; допущение — на событие в среднем 20 подписчиков (события чаще у популярных лотов, а их и смотрят больше): ~200 сообщений в секунду на всю площадку. Потолок 50 000 сообщений в секунду на копию из разбора 2.1.3 относится к модели «всем», здесь он далеко. Упрётся раньше число соединений на копию (память, `ulimit -n`) и лимиты балансировщика.
- Цена по сравнению с опросом: ещё один контейнер, один Redis, две миграции (`outbox_kind_known`, `lots.version`) и долгие соединения за балансировщиком (idle-таймаут, ping/pong).
