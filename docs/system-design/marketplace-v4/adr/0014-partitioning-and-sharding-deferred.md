# ADR 0014. Партиционирование журналов и шардирование отложены

**Статус:** принято: не делаем сейчас, пересмотр по сигналу.

## Контекст

Задание недели просит различать партиционирование (одна база, таблица разбита на секции) и шардирование (данные на разных серверах). Первое решение «разбить большие журналы по месяцам» выглядит естественно. Но в проекте деньги держатся на ограничениях базы, а у секционированных таблиц в PostgreSQL есть жёсткие правила: первичный ключ и любое `UNIQUE` обязаны включать колонки ключа секции, а исключающее ограничение (`EXCLUDE`) нельзя создать на всю секционированную таблицу, только на каждую секцию отдельно.

**Что проверено в миграциях:**

| Ограничение                                                                                                                                       | Миграция                                                | Что будет при секциях по `created_at`                                                                                 |
| ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `wallet_operations_bank_notification_key`: `UNIQUE (bank_notification_id) WHERE ... IS NOT NULL`                                                  | `InitMarketplace`                                       | придётся включить время: **одно банковское уведомление можно зачислить дважды в разных месяцах** (правило 3 потеряно) |
| `wallet_operations_deal_wallet_key`: `UNIQUE (deal_id, wallet_id)`                                                                                | `InitMarketplace`                                       | то же: уникальность только внутри месяца                                                                              |
| `deals`: `PRIMARY KEY (id)` и `UNIQUE (id, lot_id)`; на них ссылаются `wallet_operations`, `deal_receipts`, `lot_stock_history (deal_id, lot_id)` | `InitMarketplace`, `AppendOnlyLedger`, `BackgroundJobs` | первичный ключ станет `(id, created_at)`, и каждый внешний ключ на `deals (id)` придётся переписать или убрать        |
| `lot_stock_history_deal_key`: `UNIQUE (deal_id) WHERE deal_id IS NOT NULL`                                                                        | `AppendOnlyLedger`                                      | как выше                                                                                                              |
| `ip_bans_no_overlap`: `EXCLUDE USING gist (ip WITH =, период WITH &&)`                                                                            | `BackgroundJobs`                                        | не создать на всю таблицу: пересечение банов между секциями не проверяется                                            |

## Объём (допущения в [README](../README.md#оценка-нагрузки))

2000 сделок в день: около 730 тысяч сделок и ~1,6 млн строк журнала в год, порядка 160 МБ при ~100 байтах на строку. Это не «большая таблица»: она целиком помещается в память сервера, и индексы справляются.

## Варианты

1. **Партиции по месяцам для денежных таблиц.** Быстрая архивация старых месяцев (`DROP`/`DETACH PARTITION`). Платим потерей глобальной уникальности и внешних ключей, на которых стоят инварианты. **Отклонено.**
2. **Не партиционировать сейчас.** Платим тем, что при росте на порядки придётся мигрировать. Сигналы пересмотра ниже.
3. **Партиционировать только таблицы без таких инвариантов** (журнал `processed_messages` из [задачи 2.1.2](../../../highload/README.md#212-rabbitmq), если появится) и чистить `outbox`: отправленные строки старше 30 суток удалять пачками (`DELETE ... LIMIT`), частичный индекс по неотправленным уже держит выборку релея быстрой.
4. **Шардирование** по `company_id`, `lot_id` или дате.

## Выбор

**Вариант 2 плюс чистка `outbox` из варианта 3.** Шардирование не берём.

Почему не шардирование:

- Покупка — одна транзакция над лотом продавца, кошельком покупателя и кошельком продавца ([docs/db](../../../db/README.md)). Ключ `company_id` разводит покупателя и продавца по разным шардам: сделка становится **межшардовой**, вместо одной транзакции нужны 2PC или сага, и инварианты в триггерах и отложенных ограничениях (`balance = sum(journal)`, цепочка остатков) перестают быть гарантией.
- Ключ `lot_id` не помогает: кошелёк покупателя всё равно на другом шарде.
- Ключ «дата» отправляет все новые записи в последний шард: он горячий, остальные простаивают.

## Сигналы пересмотра

- Запись упирается в потолок основной базы (CPU или IOPS записи > 70%) **после** вертикального роста, кэша и реплики.
- Таблицы не помещаются в память, а запросы по времени замедлились; нужно быстро удалять старые данные (`DROP PARTITION`). Тогда сначала подумать, какие инварианты можно перенести (например, уникальность через вспомогательную непартиционированную таблицу ключей).
- Нужны разные регионы с жёсткими требованиями по размещению данных.

## Последствия

- Ограничения базы остаются настоящими гарантиями без исключений.
- Кликстрим уже вынесен из PostgreSQL (Kafka и S3), основной рост данных идёт туда, а не в журналы денег.
- Рост `outbox` закрывается чисткой по сроку; это нужно сделать раньше, чем таблица заметно вырастет (сейчас в [docs/background](../../../background/README.md) это записано как известное ограничение).
