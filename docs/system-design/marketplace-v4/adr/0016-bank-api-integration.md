# ADR 0016. Автоматическое зачисление: интеграция с API банка

**Статус:** предложено (зона 7, ещё не реализовано).

## Контекст

Сейчас банк присылает уведомление о пополнении администратору, а тот вручную вызывает `POST /companies/:id/wallet/deposits` с телом `{ bankNotificationId, amount }`. Идемпотентность уже есть в базе: `wallet_operations_bank_notification_key` — уникальный индекс по `bank_notification_id`, повтор получает `409` «Это банковское уведомление уже обработано» ([src/db/constraint-messages.ts](../../../../src/db/constraint-messages.ts)). Автоматизировать зачисление значит интегрироваться с внешним, нестабильным API; общий разбор — [docs/highload](../../../highload/README.md#211-нестабильный-api).

Допущения: банк иногда отвечает ошибкой 500 и медленно (до 30 с), квота 50 запросов в секунду, у уведомления есть собственный уникальный id и у платежа поле «назначение», по которому находится компания.

## Варианты

1. **Опрос выписки** раз в 5 минут. Просто, всегда доберёт пропущенное. Платим задержкой до 5 минут и лишними запросами.
2. **Webhook банка.** Быстро. Платим публичным эндпоинтом, проверкой подписи и тем, что потерянный webhook никто не повторит.
3. **Webhook плюс опрос как страховка.** Платим обоими механизмами; зато задержка минимальна и пропусков нет.
4. **Синхронно в запросе администратора.** Не решает задачу: зачисление остаётся ручным.

## Выбор

**Вариант 3.** Контейнер `bank-sync` (Node.js, BullMQ):

- Webhook и опрос только **кладут в очередь** уведомление `{ bankNotificationId, amount, reference }` (`jobId = bankNotificationId`: повторы схлопываются).
- Воркер определяет компанию по `reference` и вызывает **существующий** `POST /companies/:id/wallet/deposits`. Новая таблица идемпотентности не нужна: уникальный индекс `bank_notification_id` и есть замок.
- **Предварительное изменение API пополнения (до запуска `bank-sync`).** Сейчас статус `409` в проекте означает три разных исхода ([src/db/pg-error.filter.ts](../../../../src/db/pg-error.filter.ts)): `ALREADY_EXISTS` (любой уникальный индекс), `RULE_VIOLATED` (`CHECK`) и `RETRY` (`lock_timeout`, deadlock). Различать их по статусу нельзя: `409 RETRY` стал бы «успехом», и деньги не зачислились бы. По `code` тоже нельзя: `ALREADY_EXISTS` одинаков для любого уникального индекса, а какое именно ограничение сработало, видно только из русского текста сообщения, а это не контракт. Поэтому нарушение `wallet_operations_bank_notification_key` отвечает **отдельным кодом `DEPOSIT_DUPLICATE`**, а в теле — уже записанная операция: компания и сумма.
- Исходы:
  - `201` — готово;
  - `409 DEPOSIT_DUPLICATE` **и сумма с компанией совпали** — успех (повтор или параллельная копия);
  - `409 DEPOSIT_DUPLICATE` **с другой суммой или компанией** — не успех: тот же `bankNotificationId` пришёл с другими данными, задача в `failed` и алерт администратору. Сейчас такой повтор молча считался бы успехом;
  - `409 RETRY` и `503 DB_TIMEOUT` — временная ошибка, повтор с паузой и jitter;
  - другой `4xx`, в том числе компания не найдена, — задача остаётся в `failed` и попадает администратору на ручной разбор (его роль остаётся для неопознанных платежей);
  - `5xx` и таймаут — повтор с паузой и jitter (`attempts: 5`). Повтор пополнения безопасен: замок — уникальный индекс.
- **Межсервисная авторизация.** `bank-sync` вызывает эндпоинт администратора, а аутентификации в проекте нет вообще. До запуска нужен сервисный доступ: отдельный токен `bank-sync` (или mTLS внутри сети) с правом только на пополнение, и закрытый снаружи эндпоинт. Без этого любой, кто достучался до API, зачисляет деньги.
- Вызовы к банку (опрос): таймаут выше p99 банка (40 с при ответах до 30 с: опрос только читает, но короткий таймаут при деградации не дал бы ни одного ответа), circuit breaker, лимит под квоту. Пока breaker открыт, опрос откладывается, а не тратит попытки.
- **Курсор опроса — порядковый номер записи выписки**, если банк его отдаёт: он не зависит от того, каким временем банк провёл платёж. Курсор по времени с нахлёстом 10 минут — только запасной вариант: платёж, который банк провёл задним числом (позже, чем на 10 минут), он пропустит. Тогда нужна ещё ежедневная сверка выписки за сутки целиком. Дубли из нахлёста гасит уникальный индекс.
- Суммы — в целых центах, строкой; воркер не пересчитывает суммы и не придумывает собственных идентификаторов.

## Последствия

- Банк лежит час: опрос не работает, webhook не приходит, деньги не теряются: после возврата опрос добирает за период; задержка зачисления — в пределах простоя плюс 5 минут.
- Зачисление по ошибке банка (отзыв платежа) схемой **не предусмотрено**: тип операции `deposit` допускает только положительную сумму (`wallet_operations_shape`), журнал только дополняется. Для отзыва нужна миграция с новым типом операции; пока это ручное решение администратора, и это нужно сказать прямо.
- Webhook — внешняя поверхность: проверка подписи и ограничение частоты на входе, иначе ложное уведомление зачислит деньги.
- `bank-sync` нужен отдельным контейнером, потому что внешние вызовы и их повторы не должны делить пул с API. Масштабируется копиями: гонку закрывает индекс, а не число копий.
- Пока зачислений в день единицы, ручной вариант дешевле: сигнал для зоны — десятки зачислений в день и жалобы на задержку.
