# Системный дизайн: площадка дорогого оборудования, версия 2

Доработка карты роста из [версии 1](../marketplace-v1/README.md) после разбора занятия 04. Новую систему не проектируем: те же продавцы и покупатели (компании), те же четыре зоны роста, но карта приведена к единому виду, на ней появились данные и решения.

## Что изменилось по сравнению с версией 1

- **Первая версия читается отдельно.** Сплошная зелёная рамка «Первая версия» содержит всё, что работает на старте: app (интерфейс и API, воркер в одном процессе), PostgreSQL, S3, разовая задача миграций. Зоны роста нарисованы вокруг пунктиром и без неё читаются целиком.
- **Роли.** Покупатель, продавец и **администратор** (бухгалтер, зачисляет деньги). Роль «оператор» из версии 1 заменена администратором: он единственный, кто видит банковские уведомления и отмечает пополнения.
- **Система названа по делу:** «Площадка дорогого оборудования», а не `app` или `system-design`.
- **Деньги.** Платёжный шлюз убран: приём и вывод денег не делаем. Банк присылает уведомление администратору, тот зачисляет деньги, дальше все расчёты идут внутри площадки (кошельки и журнал в PostgreSQL).
- **У каждого контейнера технология и назначение**, у каждой стрелки подпись: кто читает и кто пишет (например, «Читает каталог, пишет покупки», «Реплицирует: PostgreSQL пишет, реплика читает»).
- **Файлы сразу в объектном хранилище.** S3 входит в первую версию, а не в зону роста: браузер пишет и читает фото напрямую по подписанной ссылке, app только выдаёт ссылки, в базе лежат метаданные и ключ. Зона 4 теперь только про фон.
- **Видно, кто выполняет фоновые задачи и где живёт очередь.** На старте воркер - отдельный блок внутри app (тот же процесс), очередь - таблица в PostgreSQL. В зоне 4 появляются отдельный воркер и очередь в Redis; воркер тоже рисуется со стрелками «берёт задачи» и «читает данные, пишет результат».
- **Исправлена очередь на старте.** В версии 1 была «BullMQ на PostgreSQL»; BullMQ работает только на Redis. На старте очередь - таблица в PostgreSQL (например, через pg-boss), BullMQ на Redis появляется в зоне 4.
- **Не рисуем то, чем не управляем:** браузер и DNS. SPA - это наш бандл, статика внутри app, а не отдельный контейнер и не браузер.
- **Миграции** показаны как отдельный контейнер: схему меняет разовая задача до старта app, а не сам app при запуске.
- **Зона 1, поиск:** уточнено, что ищем по названию лота, названию компании-продавца и её email, с морфологией.

## Данные: где что лежит

| Данные                                        | Хранилище                                                                      | Почему здесь                                                                                                                        | Какие нужны гарантии                                                                                                                                                                                                               |
| --------------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Кошельки** (баланс)                         | PostgreSQL, основная база                                                      | деньги: нужны транзакции, ограничения и блокировка строки; баланс обновляется вместе с журналом                                     | ACID; `CHECK balance >= 0`; `FOR UPDATE` при покупке; читаем **только с основной базы**: реплика отстаёт, кэша нет; резервные копии с восстановлением на момент времени                                                            |
| **Сделки**                                    | PostgreSQL                                                                     | неизменяемый факт, связан внешними ключами с лотом, продавцом и покупателем; создаётся в той же транзакции, что и движение денег    | ACID; составной FK `(lot_id, seller_id)`; цена и количество на момент сделки не меняются; нет ни `UPDATE`, ни `DELETE`                                                                                                             |
| **Журнал операций**                           | PostgreSQL, append-only таблица                                                | источник правды о деньгах: баланс - его сумма; уникальный индекс не даёт зачесть одно банковское уведомление дважды                 | ACID; только вставки; `UNIQUE` частичный по номеру уведомления; сверка `balance = sum(amount)`; хранится бессрочно, в кэш и в логи не выносится                                                                                    |
| **История лотов** (цена, публикация, остаток) | PostgreSQL, три append-only таблицы                                            | пишется в той же транзакции, что и текущее состояние лота; аналитике нужны запросы по времени и соединения со сделками              | ACID; одна запись на лот и момент (`UNIQUE`); читать можно с реплики: допустима задержка; при росте аналитики - выгрузка в колоночное хранилище (см. версию 1)                                                                     |
| **Фото лотов**                                | файл - S3 (объектное хранилище); метаданные и ключ - PostgreSQL (`lot_photos`) | файлы большие и общие для всех инстансов, в базе раздули бы копии и память; метаданные нужны запросам и должны быть связаны с лотом | долговечность объектов; закрытый бакет, доступ по подписанной ссылке с коротким сроком; порядок записи «файл, затем строка в базе»: осиротевшие файлы без строки убирает фоновая задача; пропавший файл - ошибка, не тихий пропуск |
| **Каталог для поиска**                        | OpenSearch (зона 1); на старте - сам PostgreSQL                                | морфология, опечатки, ранжирование и поиск по названию компании-продавца и её email                                                 | не источник правды: производная копия лотов и компаний, пересобирается из PostgreSQL; допустима задержка секунды-минуты (eventual consistency); цену и остаток при покупке всегда берём из PostgreSQL                              |
| **Очередь задач**                             | PostgreSQL (на старте), Redis + BullMQ (зона 4)                                | на старте задач единицы: не нужен ещё один компонент и можно ставить задачу в той же транзакции, что и событие                      | доставка «хотя бы раз» и идемпотентные задачи; потеря Redis не должна терять работу: задачи восстанавливаются из состояния в PostgreSQL                                                                                            |

## Кто пишет и что будет при замене (для проверки в паре)

Заготовка к вопросам «кто пишет сюда?» и «что будет, если этот контейнер заменили?».

| Контейнер               | Кто пишет                                                  | Что будет, если заменить                                                                                                                         |
| ----------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| PostgreSQL              | app (API и воркер), миграции; на старте и очередь          | менять на другую реляционную базу можно, пока есть транзакции и `FOR UPDATE`; на документную нельзя: деньги теряют гарантии (см. ADR 0001, 0002) |
| S3                      | браузер напрямую (по подписанной ссылке), воркер (очистка) | любое S3-совместимое хранилище: ключи в базе остаются прежними; Compose использует SeaweedFS, продакшен - управляемый S3                         |
| app                     | покупатель, продавец и администратор через интерфейс       | клиенты зависят только от JSON API; новый app должен сохранить правила, лежащие в базе, они выживают при замене                                  |
| Очередь                 | app (ставит), воркер (берёт)                               | переезд PostgreSQL → Redis без смены задач, если они идемпотентны и состояние остаётся в PostgreSQL                                              |
| OpenSearch (зона 1)     | воркер или app (индексация), больше никто                  | индекс пересобирается из PostgreSQL, потери данных нет; замена - это переиндексация                                                              |
| Redis-кэш (зона 3)      | app                                                        | система работает без кэша, только медленнее; деньги в кэше не лежат                                                                              |
| Реплика чтения (зона 3) | только PostgreSQL (репликация)                             | переключаем чтение каталога обратно на основную базу                                                                                             |

| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |

То же для отдельного воркера в зоне 4 и на карте v1                                                         | [L2 v2](<L2 - Containers.drawio.svg>), зона 4 на [карте v2](growth-map.drawio.svg) и [карте v1](../marketplace-v1/growth-map.drawio.svg) |
