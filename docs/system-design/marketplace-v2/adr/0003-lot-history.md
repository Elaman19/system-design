# ADR 0003. История лота: таблица на каждый независимо меняющийся атрибут

**Статус:** принято.

## Контекст

Цена, публикация и остаток лота меняются независимо и по разным поводам. Аналитике нужны цена в день сделки, число дней, когда лот был доступен, и динамика остатка.

## Варианты

1. **Снимок всей строки лота** при любом изменении. Каждая смена остатка копирует название и цену; «сколько дней опубликован» приходится выбирать из строк, где публикация не менялась.
2. **Интервалы `valid_from` / `valid_to`.** Удобно читать, но закрытие предыдущего интервала - ещё один `UPDATE` и риск дыр и пересечений.
3. **Три append-only таблицы** (`lot_price_history`, `lot_publication_history`, `lot_stock_history`): только `valid_from`/`changed_at`, конец интервала считается через `lead()`.

## Выбор

Вариант 3. Текущее состояние остаётся в `lots` (его читает каталог, на нём стоят ограничения и блокировка), и пишется в одной транзакции с историей. Время записи - `clock_timestamp()`; одна запись на лот и момент гарантирует `UNIQUE (lot_id, valid_from)`.

## Последствия

- Аналитические запросы - обычный SQL с `lead()` и `LATERAL`.
- Текущее значение дублируется историей: это осознанная денормализация, согласованность держит транзакция.
- При большом объёме аналитики историю можно выгружать в колоночное хранилище; источник правды остаётся в PostgreSQL.
