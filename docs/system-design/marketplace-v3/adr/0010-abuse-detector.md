# ADR 0010. Детектор абьюза: отдельный консьюмер, окно по времени события

**Статус:** принято.

## Контекст

Кто-то скачивает площадку скриптом: тысячи просмотров в минуту с одного IP. Нужно банить такие адреса. Простой лимит запросов можно сделать и в API, но задание просит отдельную систему, которая слушает события, не трогает код API, и в которую завтра можно добавить другие сигналы.

## Варианты

1. **Лимит запросов в API** (Redis-счётчик, `INCR` с TTL). Работает мгновенно, но живёт в пути запроса, привязан к API, другим сигналам не масштабируется.
2. **Kafka Streams или Flink.** Правильные инструменты для окон и состояния, но тяжёлая платформа и другой язык.
3. **Отдельный консьюмер `lot-views` со счётчиком в памяти.** Просто; верно, пока все просмотры одного IP попадают к одной копии (ключ топика — IP, ADR 0008).
4. **Счётчики в Redis.** Переживают перезапуск, но каждый просмотр — запись в Redis, а работа сложнее.

## Выбор

Вариант 3. `abuse-detector` в группе `abuse-detector` считает просмотры по IP в скользящем окне `ABUSE_WINDOW_MS` (60 с); больше `ABUSE_MAX_VIEWS` (300) — бан на `ABUSE_BAN_MS` (1 час) событием в `ip-bans`. Окно считается **по времени события** (`viewedAt`), а не по часам, поэтому при догоне отставания счёт верный. Событие бана определяется просмотром, пересёкшим порог (его время плюс срок, без `now()`), но после перезапуска окно пустое, и бан может выйти другим или позже; дубль гасит ограничение `EXCLUDE` в `ip_bans`, а не детерминизм события. Бан записывает отдельный `ban-recorder`; API проверяет бан запросом к `ip_bans` и отвечает 429.

## Последствия

- Детектор упал — сайт работает; поднялся — догнал и забанил с опозданием (проверено на стенде).
- Бан наступает через секунды, не мгновенно.
- Состояние в памяти: после перезапуска окно начинается с нуля, и бан может опоздать до длины окна. Лечится хранением счётчиков в Redis (зона 4 карты роста).
- Копий детектора может быть до числа партиций (3): каждая видит свои IP целиком.
- Бан, который к моменту обработки уже закончился (отставание больше часа), не публикуется.
- Запись бана идемпотентна на уровне БД: `EXCLUDE` по `(ip, период)` не допускает пересекающихся банов (ADR 0007, способ 9).
- Событие, которое база отвергает как значение (период «конец раньше начала», число не по размеру колонки), `ban-recorder` пишет в лог и пропускает: повтор не поможет и остановил бы партицию.
- Проверка бана — один индексный запрос на каждый запрос API; для масштаба — кэш (зона 3).
