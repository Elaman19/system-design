# ADR 0011. Планировщик: отдельный контейнер в одной копии

**Статус:** принято.

## Контекст

Раз в сутки администратору уходит отчёт: опубликовано лотов сейчас и за сутки, сделок и сумма за сутки. API и воркеры масштабируются горизонтально. Кто-то должен решать, _когда_ ставить задачу, и решать это один раз в сутки.

## Варианты

1. **Cron внутри API.** Каждая копия API имеет свой таймер: N копий — N отчётов.
2. **Cron внутри воркера.** То же самое для воркеров.
3. **Отдельный контейнер-планировщик, одна копия** (`@nestjs/schedule`). Таймер один, масштабируется только то, что делает работу.
4. **`upsertJobScheduler` BullMQ.** Расписание хранится в Redis по ключу, несколько копий безопасны: задача ставится один раз.
5. **Внешний планировщик** (Kubernetes CronJob, `pg_cron`). Не требует своего процесса, но привязан к платформе.

## Выбор

Вариант 3: `scheduler` — отдельный контейнер, одна копия, `DAILY_REPORT_CRON` и `DAILY_REPORT_TZ`. Он только кладёт задачу `daily-report` в очередь; письмо собирает воркер. В `docker-compose.yml` у него нет `replicas`, а тест `compose.spec.ts` следит, чтобы не появились.

## Последствия

- Копий несколько — отчётов несколько: поэтому «одна копия» записано в compose и проверяется тестом, а не держится на памяти.
- Упал планировщик в момент срабатывания — отчёта в этот день нет, пропущенное не догоняется. Для отчёта это допустимо: гарантий не требуется, outbox не нужен.
- Отчёт — сводка без денег и без события, которое надо удержать вместе с транзакцией; чек — наоборот (ADR 0006). Поэтому разные гарантии.
- Вариант 4 избавил бы от ограничения «одна копия» (дедупликация в Redis). Мы выбрали 3, потому что задание требует отдельный контейнер в одной копии и разбор причины; в продакшене с несколькими расписаниями выбор был бы за вариантом 4.
