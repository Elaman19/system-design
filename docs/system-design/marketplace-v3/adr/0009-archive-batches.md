# ADR 0009. Архив кликстрима: пачки, имя из оффсета, коммит после записи

**Статус:** принято.

## Контекст

Просмотры из Kafka нужно сложить в S3 для аналитики. Kafka доставляет «хотя бы раз»: после падения потребителя часть сообщений придёт снова. Если архив запишет их дважды, аналитика посчитает просмотр дважды. Мелкие файлы в S3 дороги и медленны, поэтому писать нужно пачками.

## Варианты

1. **Файл на сообщение.** Просто, но миллионы мелких объектов.
2. **Пачки со случайным именем + удаление дублей в аналитике.** Дубли в хранилище, чистка на каждом запросе.
3. **Kafka Connect S3 sink.** Готовое решение, но отдельная платформа ради одного потока и свои правила именования.
4. **Пачки с детерминированным именем и коммитом оффсета после записи.**
5. **Транзакции Kafka (exactly-once).** Не помогают: запись в S3 не участвует в транзакции Kafka.

## Выбор

Вариант 4 (`src/clickstream/archiver.service.ts`). Пачка на каждую партицию уходит в S3 при `ARCHIVE_BATCH_SIZE` (1000) сообщениях или через `ARCHIVE_FLUSH_MS` (60 с). Имя — `clickstream/date=<день>/<партиция>-<первый оффсет>-<последний оффсет>.jsonl`. **Сначала запись файла, потом коммит оффсета.** Записи одной партиции идут по очереди, и следующая пачка пишется только после коммита предыдущей (неудачный коммит повторяется, а не пропускается).

## Последствия

- Падение до записи — пачка не потеряна (оффсет не двигался). Падение между записью и коммитом — повторная пачка начинается с того же первого оффсета. Нарезана так же — то же имя, тот же объект; иначе — другое имя, и после коммита повтор удаляет остальные файлы с тем же первым оффсетом. Второго файла нет (тесты `crash after the file is written but before the offset is committed`, `a replay cut at other places replaces the first run's file`; на стенде 106 000 строк и 106 000 уникальных `viewId`).
- Сбой S3 блокирует партицию с повтором и паузой; чтение останавливается на следующей пачке (обратное давление), оффсет стоит на месте.
- Остаётся редкий случай ребаланса группы во время записи: `PUT` прежнего владельца, который уже ушёл в S3, ложится отдельным файлом (в имени другой последний оффсет), а не поверх файла нового владельца. Потери нет, но просмотры могут быть в двух файлах. Поэтому в событии есть `viewId`, по нему аналитика убирает копии. Первая версия называла файл только по первому оффсету, и опоздавший `PUT` короткой пачки затирал длинный файл нового владельца.
- Остановка архиватора не дописывает пачки: они перечитываются при запуске. Это даёт временный `LAG`, но не потерю.
- Папка по дню первого просмотра пачки: пачка на границе суток целиком лежит в одной папке.
