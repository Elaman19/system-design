# ADR 0006. Чек покупателю: transactional outbox и BullMQ на Redis

**Статус:** принято.

## Контекст

После сделки покупатель получает письмо с чеком. Сделка пишется в PostgreSQL, задача на письмо — в Redis (BullMQ). Общей транзакции у двух хранилищ нет, и двойная запись ломается дважды: задача внутри транзакции остаётся в Redis после отката (чек о сделке, которой нет), задача после коммита не ставится, если процесс упал между ними (сделка есть, чека не будет). Деньги и сделки не должны зависеть от доступности Redis.

## Варианты

1. **`queue.add` внутри транзакции.** Просто, но откат не снимает задачу. Недоступный Redis валит покупку.
2. **`queue.add` после коммита.** Откатов нет, но падение между коммитом и `add` теряет чек без следа.
3. **BullMQ на PostgreSQL** (есть в BullMQ 6) или pg-boss. Задача в той же транзакции, проблемы нет. Но задание прямо требует Redis, а очередь в основной базе возвращает нагрузку на неё.
4. **Transactional outbox.** Сделка и строка `outbox` в одной транзакции; отдельный релей переносит строки в очередь.
5. **CDC (Debezium) по WAL.** Без опроса, но отдельная инфраструктура ради одного события.

## Выбор

Вариант 4. `DealsService.purchase` в той же транзакции пишет строку `outbox (kind, aggregate_id)`; процесс `outbox-relay` в транзакции выбирает неотправленные строки (`FOR UPDATE SKIP LOCKED`), делает `queue.add` с `jobId = deal-receipt-<сделка>` и помечает строку. Релей опрашивает базу раз в `OUTBOX_POLL_MS` (500 мс), а не слушает WAL.

## Последствия

- API не зависит от Redis: упал Redis — покупки идут, строки копятся и уходят после возвращения (проверено на стенде).
- Доставка «хотя бы раз»: релей, упавший после `add`, поставит задачу повторно; `jobId` отбрасывает дубль, а обработчик идемпотентен (ADR 0007).
- Несколько релеев безопасны (`SKIP LOCKED`), порядок задач не гарантируется.
- Задержка чека — до `OUTBOX_POLL_MS` плюс время очереди; для письма это допустимо.
- Таблица `outbox` растёт: нужна чистка старых отправленных строк. Пока не сделана (docs/background, «Известные ограничения»).
- Опрос — постоянная лёгкая нагрузка на базу; её держит частичный индекс по неотправленным строкам (`outbox_unpublished_idx`). Если задач станут тысячи в секунду, следующий шаг — CDC.
