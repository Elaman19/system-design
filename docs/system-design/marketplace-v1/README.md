# Системный дизайн: площадка дорогого оборудования, версия 1

Сквозной кейс: продавцы-компании выставляют оборудование ценой в миллионы долларов, покупатели - тоже компании, оператор следит за сделками. Сделок единицы в день, но каждая дорогая: потерянный платёж или уведомление стоят дорого. Покупатель получает счёт и платит в срок; напоминания приходят за 2 дня, за 1 день и в день срока; просрочка - уведомление обеим сторонам; бонусы покупателю за оплату вовремя.

Принятые решения: площадка - монолит; фронтенд - SPA, бэкенд - чистый JSON API для любых клиентов (браузер, мобильные приложения, партнёры и агенты, например через MCP); HTML, если понадобится, - шаблонизатор поверх того же контента.

Это отдельная от проекта схема: диаграммы самого проекта лежат в [`docs/architecture/`](../../architecture/).

## Карта роста

![Карта роста площадки](growth-map.drawio.svg)

Исходник и картинка - один файл [`growth-map.drawio.svg`](growth-map.drawio.svg), его можно открыть в draw.io.

- **Сплошная рамка «Старт»** - с чем площадка запускается: SPA, одно приложение с API и PostgreSQL. Очередь напоминаний на старте живёт в той же базе (BullMQ умеет работать на PostgreSQL), воркер - в том же процессе, Redis не нужен. SPA на старте раздаёт само приложение.
- **Пунктирные рамки - зоны роста.** Каждая подписана тремя строками: что добавляем, зачем площадке, когда (сигнал).
- Сплошные стрелки - то, что работает на старте, пунктирные - появляются вместе со своей зоной. Когда появляется балансировщик, SPA ходит в app через него, а прямая стрелка SPA → app пропадает.
- Переход «очередь в PostgreSQL → отдельный Redis» нарисован: он в зоне 4.

| Зона              | Что                                            | Зачем                                                                      | Когда                                                                                                                    |
| ----------------- | ---------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 1. Поиск          | OpenSearch                                     | поиск по каталогу с опечатками, фильтрами и ранжированием                  | поиск в Postgres не держит p95 ~300 мс                                                                                   |
| 2. Край           | CDN и балансировщик                            | быстрый фронт для всех регионов; рост по CPU и отказоустойчивость          | CPU инстанса долго >70-80% и растёт p95; нужен запас на отказ; жалобы на задержку из других регионов                     |
| 3. Разгрузка базы | Redis-кэш и реплика на чтение                  | каталог читают намного чаще, чем пишут; не мешать записи сделок и платежей | CPU базы >70%, чтение >80% запросов, растёт p95                                                                          |
| 4. Фон и файлы    | отдельная очередь (Redis + BullMQ), воркер, S3 | напоминания не мешают API; документы сделок нужны всем инстансам           | очередь в Postgres мешает основной работе (растёт lag задач); файлы не помещаются на диск или нужны нескольким инстансам |

| Компонент                | Зона           | Зачем площадке                                                                                                     | Когда нужен, а когда нет                                                                                                                         | Как масштабируется                                                                                                     |
| ------------------------ | -------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| SPA                      | Старт          | интерфейс продавцов, покупателей и оператора; API остаётся независимым от фронта                                   | нужна всегда, пока есть веб-клиент; если клиенты только партнёры по API - не нужна                                                               | бандл статический: масштабируется раздачей (сначала приложением, потом CDN)                                            |
| app (API)                | Старт          | вся логика сделок, счетов, уведомлений и бонусов; единая точка входа для браузера, мобильных клиентов и партнёров  | нужен всегда; делить монолит на сервисы пока не нужно: единицы сделок в день, команда одна                                                       | горизонтально: инстансы без состояния за балансировщиком; состояние - в базе, файлы - в S3, конфиг - из env            |

Платёжный шлюз и email/SMS-провайдер - внешняя система: на схеме есть, в таблице нет, потому что мы их не масштабируем. Воркер шлёт через email/SMS-провайдера напоминания и уведомления (стрелка «Шлёт уведомления», HTTPS/SMTP); платежи уходят из app напрямую.

## Сигналы роста: на что смотреть

Сигналы приходят из мониторинга (занятие 07). Сейчас важно знать, какая метрика что означает.

| Компонент          | Во что упирается                            | Сигнал - какая метрика                                                                                                                               | Что делаем                                                                                                |
| ------------------ | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| app (API)          | CPU                                         | загрузка CPU всех инстансов долго выше 70-80%, вместе с ней растёт p95                                                                               | ещё инстансы за балансировщиком (зона 2)                                                                  |
| app (API)          | event loop                                  | задержка event loop (lag) >100 мс при высоком CPU одного процесса                                                                                    | вынести тяжёлую работу в воркер или `worker_threads`; инстансы помогут, только если код не блокирует цикл |
| app (API)          | память                                      | RSS растёт при неизменной нагрузке и не возвращается после GC; перезапуски по OOM                                                                    | это утечка, а не нехватка: снимок heap, чиним код; масштабирование только прячет проблему                 |
| app (API)          | ожидание, а не CPU                          | p95 растёт, CPU приложения свободен, растёт ожидание соединения из пула и время запросов к базе                                                      | искать в базе или во внешнем API (платёжный шлюз); новые инстансы не помогут, а увеличат давление на базу |
| app (API)          | единая точка отказа                         | один инстанс: перезапуск или падение - полная недоступность; ошибки 5xx при деплое                                                                   | второй инстанс и балансировщик с проверкой `/ready`                                                       |
| SPA (раздаёт app)  | сеть и CPU приложения под статику, задержка | доля трафика и CPU на статику; TTFB бандла у пользователей из других регионов                                                                        | CDN (зона 2)                                                                                              |
| PostgreSQL         | медленные запросы                           | p95 запросов выше цели, топ в `pg_stat_statements`, seq scan по большим таблицам                                                                     | сначала `EXPLAIN` и индекс; не помогло - вертикаль                                                        |
| PostgreSQL         | CPU                                         | CPU базы >70%, при этом чтение >80% запросов                                                                                                         | реплика на чтение и кэш (зона 3); если растёт запись - вертикаль                                          |
| PostgreSQL         | память                                      | cache hit ratio падает ниже ~99%, рабочий набор не помещается в RAM                                                                                  | больше памяти (вертикаль); индекс, если читаем лишнее                                                     |
| PostgreSQL         | диск                                        | свободного места <20%, растут латентность диска и объём WAL                                                                                          | чистка и архив; увеличить диск; большие файлы вынести в S3 (зона 4)                                       |
| PostgreSQL         | соединения                                  | занято >80% `max_connections`, растёт ожидание в пуле                                                                                                | пул меньше на инстанс или пулер соединений (PgBouncer): иначе 10 инстансов исчерпают лимит                |
| PostgreSQL         | запись                                      | CPU или диск primary выросли от записей, реплики не помогают                                                                                         | вертикаль, партиционирование; шардинг - только когда это уже не вытягивает                                |
| Файлы на диске app | диск и общий доступ                         | диск контейнера >70%; файл, загруженный через один инстанс, не виден другому; потеря при пересоздании контейнера                                     | S3 (зона 4): файлы не должны жить на диске контейнера                                                     |

## Сценарии роста

**Реал-тайм: аукцион, ставки видны всем, торги закрываются секунда в секунду**

- WebSocket или SSE-шлюз - рассылает ставки участникам сразу; обычный HTTP-запрос по таймеру не даёт «сразу».
- Redis pub/sub (или аналог) - доставляет ставку всем инстансам шлюза: участники сидят на разных инстансах.
- PostgreSQL с блокировкой строки лота - принимает ставки строго по порядку, иначе две ставки победят одновременно.
- Дедлайн проверяется внутри транзакции приема ставки по серверному времени (`now() < ends_at`): ставка после срока отклоняется, даже если задача закрытия ещё не отработала. Очередь с отложенной задачей лишь финализирует торги (победитель, счёт) и шлёт уведомления: занятый или недоступный воркер выполнит её позже срока, поэтому точность на неё не опирается. По клиентским часам нельзя.
- Балансировщик с поддержкой WebSocket - держит долгие соединения и снимает больной инстанс.

**Огромный каталог: миллионы позиций, от скрепок до крупной техники**

- OpenSearch - поиск с фильтрами и ранжированием по миллионам позиций.
- Очередь и воркер - обновляют индекс при изменении товара, не блокируя продавца.
- Кэш - карточки популярных позиций и выдача частых запросов.
- S3 и CDN - фото и документы, их много и они тяжёлые.
- Реплики чтения и keyset-пагинация - большие списки без `OFFSET` и без нагрузки на primary.

**Весь мир: продаём по всему миру, везде должно работать быстро**

- CDN - фронт и статика рядом с пользователем.
- Гео-DNS и приложение в нескольких регионах - ближайший сервер отвечает быстро.
- Реплики чтения по регионам - каталог читается рядом; запись сделок и платежей остаётся в одном регионе-лидере, потому что деньги требуют строгой согласованности.
- Очереди по регионам и повторная доставка - уведомления не теряются при сбое канала между регионами.

**Аналитика: много данных о поведении - что смотрят, ищут, бросают в корзине**

- Брокер событий (Kafka) - принимает поток событий от SPA и приложения, не нагружая основную БД.
- Колоночное хранилище (ClickHouse) - отвечает на аналитические запросы по большим объёмам: основная БД на это не рассчитана.
- Воркер-потребитель - превращает события в агрегаты и складывает в хранилище.
- S3 - сырые события, чтобы пересчитать историю при смене модели.

**Свой сценарий: партнёры и агенты работают через API (например, через MCP)**

- API-шлюз с ключами - узнаёт партнёра и отделяет его от пользователей SPA.
- Rate limit и квоты (в шлюзе, счётчики в Redis) - один партнёр не должен выбить площадку у остальных.
- Ключи идемпотентности для сделок и платежей - повтор запроса агента не создаёт вторую сделку.
- Очередь вебхуков и воркер - уведомляют партнёров об изменении сделки с повторными попытками.
- Версионирование API и аудит-лог - партнёры не ломаются при изменениях, а оператор видит, кто что делал.

## Продвинуто: чего нет на карте

- **Документная база (MongoDB)** - пока не нужна, потому что данные площадки связаны и требуют транзакций (сделка, счёт, платёж, бонус), а каталог умещается в Postgres с `jsonb` для разнородных атрибутов. Вернуться, если атрибуты оборудования станут настолько разными, что схема в Postgres начнёт мешать.
- **Колоночная база (ClickHouse)** - пока не нужна, потому что аналитики мало: единицы сделок в день. Нужна в сценарии «аналитика», когда события измеряются миллионами (см. выше).
- **Брокер (Kafka)** - пока не нужен, потому что очередь задач закрывает BullMQ, а потоков событий и нескольких независимых потребителей нет. Нужен вместе с аналитикой: много событий, несколько потребителей, повторное чтение.

## Что изменилось после критики напарника

Заполняется после встречи пары: что спросил напарник, какие зоны и сигналы поменялись. Встреча ещё не состоялась, поэтому здесь пока ничего не записано.
